# 0001 课表的权威来源：服务端档案与调课记录

- 状态：已采纳（2026-10-24）
- 范围：服务端、ClassIsland 插件、手机/手表/WebUI 的课表显示与换课

## 背景

同一个班的课表原先有三份，互不自动对齐：

1. 服务端班级档案：网页编辑，保存后不下发，也没有“哪个版本已部署到哪个班”的记录。
2. 教室端 ClassIsland 档案：实际运行的那份。换课、永久换课、改任课老师、调休临时课表、老师在 ClassIsland 里的修改都只改它。
3. 服务端课表缓存：插件上报的七日课表，同步过一次后网页就一直显示它。

换课是向教室端逐节发出的命令，服务端只留申请记录和单节任课老师覆盖。因此档案下发、调休规则变化、临时层下发都可能静默删掉换课的临时层，而申请仍显示“已通过”；临时层是当天课表的冻结副本，基础课表变化后不跟着变，按节次索引的老师覆盖可能落到错误的节次上；网页、手机、手表直接换课不留记录，可能撤销已批准的换课；撤回可能因课位已变化而卡住。

## 决策

1. **基础课表以服务端档案为准。** 教室端是执行者。教室端本地改动应被检测并收回到档案（服务端自上次部署后没改过时自动收回为新版本，双方都改过时由人选择），而不是被静默覆盖。这部分在阶段二实现。
2. **单日调整以服务端调课记录为准。** 每条调课记录是“某班某日某节从基础科目 A 改为 B”，带守卫（A）。同一课位可叠放，序号最大的生效，撤回上层回落到下层。
3. **插件按“基础课表 + 调课 + 调休”生成托管临时层。** 服务端下发调课集合（期望状态，带版本），插件组合后写入当天临时层并在课表推送中回执：每条调课的结果（已生效/冲突）、本地产生的调课、无法托管的日期。临时层可随时重建：基础课表或时间表变化、临时层丢失、调休变化时都按同一规则重新生成。
4. **所有临时调整都汇成调课记录。** 换课申请直接写入；RemoteCI 的临时换课命令（课表页、手机、手表、局域网）与在 ClassIsland 里改托管临时层，由插件转为本地调课上报，服务端按 ID 幂等收编。外来临时层与基础课表节数相同时接管，否则该日不托管、服务端调课回报冲突。
5. **冲突不静默。** 守卫对不上、放假、外来临时层、插件过旧等都回报冲突码；服务端把相关调课置为失效，换课申请变为“已失效”并通知申请人、对方老师与相关班主任。
6. **需要升级插件。** 插件在线但不支持 `schedule.adjustments` 时换课被拒绝并提示升级，不保留旧的逐节命令路径。

## 后果

- 网页、手机、手表与 ClassIsland 看到同一份生效课表；教室端离线时服务端按调课记录显示并标记待生效，上线后补发。
- 撤回只需撤销记录再下发，不依赖教室端当前课表，不会卡住。
- 档案下发、调休变化之后，换课要么按新基础课表继续生效，要么失效并通知，不会再“记录显示已通过、教室端却没了”。
- 插件需要在 UI 线程解析“忽略临时层的基础课表”：SDK 没有对应接口，插件临时摘掉该日预定课表查询后立即放回，期间不保存。定时核对沿用记录的基础课表，只在调休、档案应用、学期变化、跨天时完整解析。
- 服务端与插件的旧数据需要迁移：服务端启动时把旧换课回填为调课记录；插件首次运行时接管旧版调休临时课表，其中旧换课的改动转为本地调课。
- 旧版插件的班级在升级前不能换课。
